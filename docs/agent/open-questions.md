# Решения ревью и оставшиеся вопросы

Общая архитектура одобрена с поправками; они внесены в
[architecture-proposal.md](architecture-proposal.md) и
[implementation-plan.md](implementation-plan.md). Текущее задание ограничено
документами. Реализация приложения и длительного ручного режима не начата.

## Принятые решения

| Вопрос | Решение ревью |
|---|---|
| Порты | Workbench UI API — `127.0.0.1:7430`; Runtime TCP `7420` и WebSocket `7421` остаются за Runtime |
| Основная операция UI API | `document.replace` с instance ID, CAS revision и атомарной валидацией |
| Typed patch | Описание шести операций сохранено; реализация только после работающего вертикального среза с Clojure, не условие первой версии |
| Ранний результат | Clojure задаёт документ → Workbench получает данные из Runtime → `egui_plot` показывает живой график |
| Мощность | Принят `output_observation` по `output.readback.value/at`: подтверждённые дискретные значения, маркеры без интерполяции пропусков; не независимое непрерывное физическое измерение |
| Подтверждения | Обычная уставка в прежнем режиме — явный Apply и проверка revision; дополнительные подтверждения для потенциально опасных операций и смены режима |
| Ручное продление | Подтверждение каждого renew при lease 2 секунды непрактично для длительного эксперимента; отдельно предложить явный режим с видимым автопродлением, пока не реализовать |
| Основа интеграции | Сохранены корректный bootstrap, domain fences, bounded queues, RAM-only состояние и запрет повторения неопределённых mutations |
| Границы ответственности | Runtime владеет безопасностью и полномочиями; Workbench и Clojure имеют отдельные scope; UI API не становится Runtime gateway |

Без изменений остаются одно окно/один Runtime, стандартные eframe/egui/egui_plot,
layout без плагинов, optional history через API, локальная модель доверия и
предложенные стартовые лимиты. Принятие архитектуры не даёт разрешения создавать
исходники в текущем задании.

## Для следующего обсуждения: длительный ручной режим

Полное предложение — раздел 6.4 архитектуры. Предлагается один явный вход
«Включить ручное управление» с согласием на автоматические renew, постоянный
индикатор режима/выхода/остатка lease/результата renew и отдельная кнопка
«Завершить ручное управление / Safe». Изменение выхода остаётся отдельным
Apply с подтверждением физической операции; автопродление не повторяет write.

Каждый плановый renew — новая mutation своего scope после известного успеха
предыдущей, а не повтор неопределённого запроса. При потере Live, ошибке/unknown,
смене fences/владельца или пропуске временного бюджета режим приостанавливается.
Reconnect не включает его заново, не делает renew/reacquire и не восстанавливает
старый выход. Safe остаётся запросом до `safe_confirmed`. Закрытие/крах Workbench
прекращает renew; последствия конечной lease определяет Runtime.

Обсудить перед реализацией:

| Пункт | Предложение и ограничение |
|---|---|
| Частота renew и запас | Для lease 2 s начать с кандидата 500 ms; проверить round trip, поздние ответы и консервативную оценку остатка. Отправка/accepted не продлевают countdown оптимистически |
| Занятый выход | Runtime разрешает renew только idle lease; write может длиться дольше срока. Не копить renew и не обещать непрерывного удержания права при долгом I/O; при пропущенном окне/ошибке приостановить режим |
| Сворачивание | Рекомендация: потеря focus/сворачивание сами не отключают явно включённое управление, это заранее поясняется. После сна/задержки сверх бюджета — приостановка без автоматического возобновления |
| Завершение | Явный Safe прекращает планирование renew и запрашивает безопасный переход; unknown admission сначала требует выяснить seq. Для закрытия предложить явный выбор «Safe и закрыть» |
| Видимость режима | Постоянный статус/Safe в системной части GUI: внешний `document.replace` не должен удалить единственную индикацию продолжающегося автопродления |

Новый safety engine, bypass OutputAuthority, продление чужой lease, скрытый acquire
или автоматический retry не предлагаются. Режим не включается UI-документом,
подключением клиента или обычным heartbeat. Он хранится только в RAM.

## Остальные вопросы реализации

**Нагрузка.** Стартовые пределы подходят первому сценарию, но не являются измеренной
производительностью. При необходимости сотен сигналов/высоких частот сначала
определить целевой профиль; это не причина менять renderer заранее.

**Классификация дополнительных подтверждений.** Базовое решение уже принято:
обычная уставка — Apply с revision, смена fixed↔ramp/темпа ramp и опасные действия —
дополнительное подтверждение, Pause/Safe — без дополнительного modal.
При появлении конкретных configuration-only properties уточнять их поведение
по смыслу операции, не возвращать общий modal на каждое редактирование.

## Подтверждённые ограничения текущего API

1. Нет единой атомарной snapshot operation для всего Runtime. Domain fences
   и query invalidation — клиентская стратегия; общий «эксперимент свеж целиком»
   не обещается.
2. Один общий frozen projection slot на connection, TTL 5 секунд; snapshot families
   читаются последовательно.
3. Recorder lifecycle events не гарантируют непрерывное обновление его counters.
4. Output readback не имеет signal generation; границы берутся из boot, authority
   instance/epoch и resource bindings, когда они доступны. Readback не является
   signal с гарантированно доступной measurement history.
5. `property_configure` на изученном wire поддерживает integer/text, не произвольную
   запись всех scalar types.
6. Controller lifecycle mutations не принимают expected_revision; гонку между
   независимыми клиентами окончательно разрешает Runtime.
7. `output_renew` ограничен собственной idle manual lease и Runtime profile;
   pending/in-flight delivery может блокировать renew.
8. Нет cross-boot exactly-once и вечного operation status. Полный restart Workbench
   уничтожает локальные pending identities по принятому требованию.

Эти ограничения не обходятся прямым доступом к lab-core или рабочей SQLite.
Они не требуют изменений Runtime для утверждённого вертикального среза.

## Проверить при начале реализации по отдельному заданию

- Совместимые версии crates/MSRV. Кандидат на дату исходного исследования:
  eframe/egui 0.37.0 + egui_plot 0.38.0; сборка сейчас не выполнялась.
- JSON Schema либо полную таблицу полей по DTO. Первый UI API объявляет только
  hello/get/replace/status; patch до реализации — `unsupported_operation`.
- Contract fixtures для bootstrap/unfenced query, late events, нового boot и
  bounded queues. Правила unknown outcome остаются обязательными и для renew.
- MIT notices при переносе функций legacy. У com_port_reader в просмотренном
  snapshot отдельный LICENSE не найден; перед буквальным переносом уточнить
  разрешение/лицензию. Независимая реализация небольших helpers остаётся альтернативой.

Следующее обсуждение касается прежде всего UX длительного ручного управления.
Не переоткрывать уже принятые решения о порте, replace, readback и базовых подтверждениях.
