# Вопросы архитектурного ревью

Основное предложение: [architecture-proposal.md](architecture-proposal.md).
Ниже решения продукта и границы гарантии, а не список препятствий для проектирования.

## Решения, которые предлагается принять

| Решение | Рекомендуемый вариант | Альтернатива и цена |
|---|---|---|
| График мощности печи | Typed `output_observation` по readback/value/at с явной подписью | Только signal curves: текущая печь не даст power plot; потребуется отдельное развитие Runtime API |
| Scope и права | Workbench получает собственный scope, внешний UI API не принимает credentials/Runtime request IDs | Shared scope нарушает модель attached connection и смешивает полномочия клиентов |
| Внешний Runtime gateway | Не включать, Clojure обращается к Runtime напрямую | Дополнительная модель полномочий, correlated outcomes и согласия оператора |
| Partial UI changes | Шесть typed patch operations плюс whole replace, общий CAS | Только replace проще; достаточен для маленьких документов, но каждое добавление кривой требует всего документа |
| Ручное управление | Явные acquire/renew/write/safe, без автопродления | Auto-renew только после отдельного согласования семантики; это уже автоматическая управляющая политика клиента |
| Начальный layout | Одно окно, панель слева, графики вертикально | Docking/layout tree увеличивает схему и тесты, пока не нужен |
| Управляющий набор | Reference, PID lifecycle/configuration, Recorder и manual output | Read-only + Reference проще, но это промежуточная версия, а не полный заявленный сценарий |
| История в v1 | Live + optional короткое RAM window, явные разрывы | Durable browser требует paging/job/cursor UX, но не улучшает guarantees при выключенном Recorder |
| Локальная модель доверия | Loopback для доверенных программ одного пользователя | Token или OS IPC при необходимости разграничения локальных пользователей |
| Размеры | 32 plots, 128 curves, 256 controls, 64 sources, bounded points | Скорректировать по ожидаемому числу сигналов/частоте; бесконечные бюджеты не разрешать |

## Что требует предметного обсуждения

**Мощность.** Устраивает ли для первого сценария график подтверждённого состояния
actuator, с обозначением readback и симуляции? Он полезен для виртуальной печи,
но не равен независимому измерению электрической мощности. Рекомендуется принять
его и сохранить возможность привязать настоящий signal у другого прибора.

**Короткие manual leases.** Профиль печи допускает 2 секунды. Подготовка draft до
acquire и явное renew работоспособны, но неудобны для постоянного ручного управления.
Рекомендуется не скрывать срок и использовать Runtime PID для продолжительных
экспериментов. Если нужен режим постоянного ручного оператора, его UX и семантику
продления рассмотреть отдельно, не маскировать под сетевой heartbeat.

**Подтверждения.** Рекомендуется explicit Apply и подтверждение изменения
уставки/включения/конфигурации/physical write; Pause/Safe — явная кнопка без
дополнительного modal. Политика не выключается внешним документом. Уточнить,
какие неопасные configuration-only properties достаточно подтверждать одним Apply.

**Нагрузка.** Предложенные пределы подходят первому лабораторному сценарию, но
не являются измеренной производительностью. Если ожидаются сотни сигналов и
высокие частоты, до расширения бюджета нужен целевой профиль. Сначала выбрать
нужные bindings/видимые ranges, а не менять renderer.

## Подтверждённые ограничения текущего API

1. Нет единой атомарной snapshot operation для всего Runtime. Domain fences
   и query invalidation — клиентская стратегия; общий «эксперимент свеж целиком»
   не обещается.
2. Один общий frozen projection slot на connection, TTL 5 секунд; snapshot families
   читаются последовательно.
3. Recorder lifecycle events не гарантируют непрерывное обновление его counters.
4. Output readback не имеет signal generation; границы берутся из boot, authority
   instance/epoch и resource bindings, когда они доступны.
5. `property_configure` не является произвольной записью всех scalar types:
   на изученном wire поддержаны integer/text.
6. Controller lifecycle mutations не принимают expected_revision; гонку между
   независимыми клиентами окончательно разрешает Runtime.
7. Нет cross-boot exactly-once и вечного operation status. Полный restart Workbench
   уничтожает локальные pending identities по принятому требованию.

Эти ограничения не требуют менять Runtime для предложенной первой версии.
Нельзя «исправить» их прямым доступом к lab-core или рабочей SQLite.

## Проверить при начале реализации

- Совместимые версии crates/MSRV. Кандидат на дату исследования:
  eframe/egui 0.37.0 + egui_plot 0.38.0; сборка сейчас не выполнялась.
- Зафиксировать JSON Schema или эквивалентную полную таблицу полей по утверждённым
  DTO. Архитектурные примеры валидны как JSON, но DTO ещё не реализованы.
- Contract fixtures для согласования unfenced query с отложенными events и
  нового bootstrap при изменении конфигурации.
- Сохранение необходимых MIT notices при переносе функций legacy.
  У com_port_reader в просмотренном snapshot отдельный LICENSE не найден;
  перед буквальным переносом кода уточнить разрешение/лицензию. Независимая
  реализация небольших helper-функций остаётся простой альтернативой.

После ревью обновить предложение и зафиксировать принятые решения. Реализация
не должна начинаться автоматически от самого наличия этого документа.
